# LingXia 0.23.0

This release changes which lxapp channel opens by default: it is now `release`
in every service environment, and a draft is something you select on purpose.
`lingxia publish --channel draft` prints a scan link and a QR code that opens
that draft in any host pointed at the same server. The rest is startup fixes:
Android 5 WebViews boot again, iOS installs signed with a free team find their
resources, and native pages get the capsule CSS variables the guide documents.
Host apps rebuild against the 0.23.0 SDK and native library together.

## Breaking changes

### The default lxapp channel is `release` on every service environment

A host running the `dev` service environment used to open `draft` lxapps by
default and `lingxia publish --env dev` used to publish to `draft`. Both now
default to `release`; `draft` needs an explicit selector.

- Pass `channel: 'draft'` to `navigateToApp` / `lx.surface.open`, or
  `--channel draft` to `lingxia publish`, where you relied on the `dev`
  default.
- An App Link without `channel` opens `release`, unless that lxapp is already
  running on another channel (see below).
- Installs and storage stay keyed by channel, so nothing is migrated or lost:
  switching service environment alone no longer selects a different set of
  lxapp data.

## Writing an lxapp

- An omitted `channel` keeps the channel the lxapp is already running on. A
  draft opened from a scan survives pin clicks, notification taps, App Links
  and `navigateToApp` calls that do not name a channel; only an explicit
  selector for a different channel replaces the session.
- Selecting a different channel retires the running session, waits for its
  Logic worker to exit, and opens the selected channel with its own storage.
  Opening the same channel again reuses the live session, and a pending
  same-channel update is still deferred to the next cold start.
- `lx.scanCode` accepts a `/lxapp/open` link on the current HTTPS
  `lingxiaServer` origin (same scheme, host and effective port) as an in-app
  open, so a draft QR works without an OS App Link association. Host-bundled
  control surfaces never switch to a downloaded draft.
- Native pages now set `--lx-page-chrome-capsule-{top,right,bottom,left,width,height}`
  as the guide documents (`0px` without a capsule). The native bootstrap
  defines `lxPageChrome` before the page runtime, so these were previously
  missing on devices.
- Pages start on Android 5.1 WebViews again. The View scripts the runtime
  injects before polyfills load are plain ES5 and no longer reference
  `globalThis`, and the legacy `JavascriptInterface` message path no longer
  drops messages, so a page no longer waits ten seconds for Logic state and
  gives up.

## Embedding a host app

- An iOS build re-signed with a free Apple team (bundle id rewritten to
  `com.TEAM.<name>-dev`) finds its SwiftPM resource bundle again. `lingxia
  install` points `CFBundleName` at the resource bundle stem, keeps the
  product name as `CFBundleDisplayName`, and moves localized `CFBundleName`
  strings to `CFBundleDisplayName` so translated launcher names survive.
- Android 5 hosts: the route fields read by the legacy bridge thread are now
  `volatile`, and messages on that path report the last top-level navigation
  URL for diagnostics instead of an empty string.

## CLI

- `lingxia publish --channel draft` prints an HTTPS `/lxapp/open` link on the
  publish server origin and, in an interactive terminal, a QR code: an image
  in iTerm2, WezTerm, Kitty and Ghostty, text elsewhere. Under tmux or screen,
  or when output is redirected, only the URL is printed. An HTTP server cannot
  produce the scan trigger. The link selects the draft channel, not a fixed
  package revision.
- `--env` no longer influences the publish channel; it still selects the
  server and token and decides whether an update signing key is required.
- `lingxia install` for iOS no longer aborts when several resource bundles
  carry an `app.json`; it warns and leaves `Info.plist` alone.

## Dependencies

- `acorn` is a development dependency of the `packages/` workspace, used by
  the View-script compatibility tests.
